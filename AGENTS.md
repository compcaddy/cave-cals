# Cave Cals project guidance

## Scope and architecture

- Native SwiftUI / SwiftData app, iOS 17+, project and scheme `CaveCals`, bundle `com.philstarkovich.cavecals`. ECC2 is an alias of this repository.
- iPhone is the target device family. Verify core functionality on iPad in iPhone compatibility mode too, especially subscriptions.
- **Cave Cals Dev** is a shared-source scheme using `Dev Debug` / `Dev Release` with `CAVE_CALS_DEV`. Its app ID is `com.philstarkovich.cavecals.dev`, widget group is `group.com.philstarkovich.cavecals.dev`, and links use `cavecals-dev://`. Dev has no CloudKit/HealthKit/App Attest entitlements; its SwiftData store explicitly uses its own sandbox with cloud off. Never give Dev the normal app's container, group, or identifier. Settings → Reset Test Data schedules a Dev-only cold-launch wipe before any stores open, then restarts onboarding; it retains developer access settings/credentials and server quotas. Purchases/restores and usage reporting are disabled in Dev; authorized private AI test access is still available. Build/setup details are in README. `scripts/configure_dev_build.rb` maintains the extra configurations without duplicating targets; the project generator calls it too.
- Backend instructions are in `backend/AGENTS.md`; read them before backend work. Preserve local-first manual logging and server-verified paid AI access.
- Read `README.md` for architecture and `Documentation/Release/Readiness.md` for dated release evidence. Never confuse local changes with an uploaded TestFlight build.

## Current UI decisions (updated September 25, 2026)

- Two states on one screen. **Home**: date header (person + chart + cog), the `DailySummaryCard`, then the day's log under a small orange left-aligned “Today” label (or the date, e.g. “Sept. 22nd”; shown only once something is logged). While today has nothing logged, Home shows **Quick Start** (orange lightning label, `homeQuickAddHeader`) below the log: up to ten Quick Add picks, kept to foods for starting the day at this hour (October 7, 2026: at least a quarter of a food's recent logs fall between an hour before now and three hours after, so at 7 AM nothing usually logged after 10 AM shows, and a noon starter sees what they log from noon to 3 PM; pins too; `FoodHistory.startsDay`, unit-tested; add mode's Quick Add is unchanged), in a short scrolling list (`homeQuickStartList`) sized to three and a half rows, with the half row fading out to invite scrolling. Names stay on one line with an ellipsis so every row is the same height. Its cards are inset 28 pt from the screen edges and use `FoodRow(compact:)`: 16-pt one-line names, 17-pt calories, a 29-pt + circle, and 44-pt rows. The empty-day message reads “No log yet.” They stay while being used, so several can be added; an added pick leaves after its confirmation (the next suggestion fills in, existing rows never reorder) unless it's usually logged more than once a day and today's count is below that usual number (`FoodHistory.expectsAnotherToday`). Search/add mode, Voice Log, Meal Scan, or Barcode Scan while viewing Today retires the picks for the rest of that day (`homeQuickAddDay.v1`); backfilling another day does not. A small gray × right-aligned on the “Quick Add” label row (lined up with the + buttons, `dismissHomeQuickAdd`) also hides them for the day. Settings → Home → **Show Quick Start on new days** (`showsHomeQuickAdd.v1`, on by default, local only) turns them off entirely. The header date shows “Today” followed on the same line by the full date (“Fri, Sept. 25th”) in small gray text, with extra space between them and tighter spacing to the chevrons; every other day (including yesterday) shows only the full date. No pills on home. **Add mode**: tapping the search field hides the date and totals and shows the pills **Logged** (labelled “Today”/the date; identifier stays `Logged`) with the hand-drawn checkmark, **Quick Add** (selected on entry) with the lightning bolt, and **Meals** with the covered dish; the search field goes full width and the capture icons hide. **Cancel** (the in-field button when empty) returns home. An orange back chevron (`addModeBack`) sits inline just left of the pills and also returns home. Do not use emoji in the pills or add a duplicate Suggestions heading.
- First-days guide (restored October 7, 2026; it was dropped in the September 17 redesign): while Today has nothing logged, Home shows gray hand-drawn arrows just above the footer (`loggingGuide`, below any reminder card). Up top, “Manually add calories (e.g., 650) / or search for any food” (the “or food (e.g., two hard-boiled eggs)” line was dropped October 7, 2026) with a long arrow down to the search field, lifted 22 pt above the capture labels so the arrow is longer; just above the capture buttons, **Voice Log**, **Barcode Scan**, and **Meal Scan** with short arrows. It hides in add mode, while searching, and under the Undo banner, and stops for good once food has been logged on two different days, so it never shows from the third day on (`LoggingGuide.shows`, unit-tested). Hidden with `--uitesting`/`--screenshots` unless a DEBUG test adds `--logging-guide`.
- The app opens on Home with the keyboard closed. Brief background/foreground transitions preserve the state, query, and date; after at least 30 minutes in the background reset to today's Home. The Search/Add shortcut opens add mode with the field focused; other logging shortcuts open their requested action. Day rollover remains supported.
- A single search field stays anchored at the bottom beside the voice, barcode, and meal-scan actions. The footer occupies its own fixed-height row below the clipped scrolling list (not a bottom safe-area inset); it moves above the keyboard, with reminders above the controls. Home honors the keyboard's safe area only while its search field has focus (`footerFollowsKeyboard`, until the keyboard has hidden), because iOS sometimes leaves a stale keyboard inset that floated the footer above a blank strip (September 30, 2026); the footer's surface color runs down behind the keyboard. No log rows may appear beneath the footer. There is no Quick Calories grid (removed September 25, 2026); typing a number in search adds calories. Food plus calories (`pizza 300`, `pizza, 300 cal`, `300 cal pizza`; parsed by `QuickEntryText`) shows an `Add "pizza" · 300 calories` row that logs in one tap; a bare trailing number must be at least 10 so counts like `eggs 2` stay searches. No separate Search button or floating Close button.
- Typing replaces the list with existing manual/numeric add, common-food, local-history, saved-meal, and online results and hides the pills. **Clear** empties the text and returns to add mode's pills; **Cancel** returns home. A successful search-result add clears the query, returns home, and scrolls to the newest row, keeping the field focused (keyboard up, **Cancel** in the field) so the next food can be typed immediately. Tapping that focused field opens add mode's pills; **Cancel** or scrolling dismisses the keyboard. The pinned `Add "query"` row above the search field (`manualSearchEntry`) uses the same orange (+) as result rows, lined up with them (20-pt trailing), with 8 pt above and below; it opens the editor to enter calories.
- Search has one red in-field text button: **Clear** while there is text (empties the field, stays in add mode) and **Cancel** when empty (returns home). Identifiers `clearSearch` / `cancelAddMode`. Hide the Results heading for numeric calorie input.
- Each changed search query starts scrolled at the top, including when the matching row IDs are unchanged. API responses arriving for that query do not reset scrolling. History matches resolve synchronously and always appear first, followed by saved meals, built-in foods, then API matches; never alphabetize these sources together.
- Search typing performance (September 30, 2026): Home re-renders on every keystroke, so never compute matches in `body` directly. `LocalFoodSearch` (in `MainView.swift`) memoizes each query's history and built-in matches per diary revision (`AppStore.entriesRevision`, bumped in `refresh()`), using a `FoodHistory.SearchIndex` whose relevance scores are query-independent and built once (prewarmed 2 s after a diary change while Home is idle; rebuilt when older than 10 minutes). Built-in results are capped at the best-ranked 50 (`LocalFoodSearch.commonLimit`; a one-letter query matches thousands) and de-duplicated against history with a Set. `CommonFoods.matching` uses dictionary indexes. The online search cache is written to disk only when it changes, on a background queue. Measured in a Debug simulator build with 1,500 entries: typing “m” went from ~1.2 s to ~18 ms per keystroke.
- Editors, camera, voice, settings, and calendar can still use sheets. Canceling an editor returns to the home screen without creating a search sheet.
- The daily weigh-in reminder is not part of the footer: it's a separate outlined card (orange border, semibold orange text, trailing chevron) on the page just above it, with the dismiss × outside the card. Identifiers `weighInReminder` / `dismissWeighIn`.
- Done eating (September 27, 2026, local only): on Today, once something is logged, a matching outlined card **Done eating for today** (check icon, no chevron; `finishDay`) appears from 6 pm, or earlier once the day reaches 90% of its calorie goal, with × (`dismissFinishDay`) to hide it for the day. Tapping it replaces the search/capture footer with “Day done. Cave closed.” and an orange **Reopen** link (`dayDone` / `reopenDay`) and hides Quick Start. Logged rows stay editable. Logging anything more for today (including Siri, widgets, shortcuts, and Duplicate) reopens it; edits, deletes, and later backfills don't. Only today can be marked; past days keep their marks. Marks live in `finishedEatingDays.v1` (per iPhone, not synced). Settings → Home → **Show “Done eating” button** (`showsFinishDay.v1`, on by default) turns the card off. Progress treats a done day, including today, as complete even when it's below the 60% rule.
- Meal types (October 6, 2026; see `Documentation/MealTypes.md`): Settings → **Meal types** → **Track meal type** (off by default; off shows no meal types anywhere) and **Set meal by time of day** (on when tracking starts). Each meal type has one block of time or none (defaults: Breakfast 5–9 AM, Morning Snack 9–11, Lunch 11–2 PM, Afternoon Snack 2–4, Dinner 4–8, Dessert no time, Evening Snack 8 PM–4 AM); snacks at different times are separate types. Types can be renamed, retimed, reordered, added, or deleted (deleting a used type hides it so its food keeps the label); overlapping times are refused, with a one-tap **Shorten <neighbor>** when the overlap is at one end. Stored as `UserProfile.mealSettingsData` (synced) and `CalorieEntry.mealType` (type id; nil = unspecified; existing entries are never rewritten). `AppStore.add` assigns the meal: a picked one, else by time of day, else none (also none outside every time). Copies logged again (Quick Add/history, Duplicate, Today list, Siri, barcode cache, saved meals) never carry the original's meal. Set by time of day, adding stays one tap. With time of day off, every one-tap add opens the filled-in editor with the meal chips showing (scrolled into view, no keyboard); saved meals pick in Add Meal and Review Scan shows one choice for all its foods. The editor's **meal type** row sits above Time for logged food (collapsed, with None) and for new food while asking. Home groups a day that has any meal into orange meal labels with calorie subtotals (section headers, list order, **Other** last for food with no meal); days without meals keep the plain "Today" list. Long-press → **Move to**. Before release, the new CloudKit fields must be deployed to production: these two plus `CD_progressSettingsData` on `CD_UserProfile` (synced Progress settings).
- October 7, 2026 review: add mode's **Today** pill is hidden (`showsLoggedPill`), leaving Quick Add and Meals. “No log yet.” hides while the first-days guide shows. With meal types on and **Set meal by time of day** on, Home groups food without a meal by its logged time (display only; a picked meal wins; outside every time → Other). Review Scan rows show how much (`ServingCount`, unit-tested): one countable thing as the total (“2 slices”, “3 bananas”), a measured serving as size × count (“1 cup (240 ml) × 2”, “100 g × 1.5”), one serving as just the serving (“1 plate”). **Add All** shows even for one food (the row's + still works). Settings' Hidden from Quick Add list starts collapsed; Tell the tribe rows have SF Symbols. Your target: orange pencils beside **Daily calories** (`planEditCalories`) and **Daily macros** (`planEditMacros`, grams become editable and stop following the calorie number); a tap anywhere in those boxes, right on the digits too, selects the whole value (`selectValueOnFocus` selects again after the tap places the cursor); “How we worked it out” shows resting burn + activity + the pace's change. The caveman's scan loop starts as he drops in. The discount box has a red × (`clearDiscountCode`). Home's narrow “search / add” prompt shrinks to fit beside the capture buttons, never cut off.
- Home log rows show only time, food name, and calories, without a macro line. Names/calories use 18-point adaptive Schoolbell text with primary color at 0.92 opacity; narrow time-to-description spacing and compact rows. Home's log rows (content and card, `homeLogOpacity`) sit at 80% opacity so the totals above lead; the “Today” label, Quick Start, and add mode's Today list stay full strength. Header spacing is deliberately tight. Tapping a logged row edits it (the editor opens with the calories selected so typing replaces them). Swiping left shows a gray **Duplicate** beside the red **Delete**; a full swipe deletes. Long-press offers Edit / Duplicate / Delete. Duplicate logs a new copy on that day at the current time. Keep swipe-to-delete red for meal rows too; do not let the orange app accent tint destructive actions. Logged rows end with a gray, non-interactive pencil.
- The home summary is one `DailySummaryCard`: a 52-point adaptive Schoolbell calorie total with a tighter top inset (thickened with `InkBoldText`, since Schoolbell has no bold weight) with `/ 2,100 cals` (or `cals` without a goal) and “N left”/“N over” (red) on one baseline, then a 10-pt calorie bar (orange; red when over goal). When macros are tracked, three columns show, each centered in its column, a hand-drawn orange cave icon (`CaveProtein`/`CaveCarbs`/`CaveFat`, sized by height so narrow art keeps no side padding) + uppercase name (centered on only half the icon's width, so the name sits slightly left) and a bold whole-gram amount with `/ goal g`, above a full-width thinner 6-pt bar that stays orange past the goal (exceeding protein is often intended). No percentages. Accessibility identifiers `calorieSummary` and `dailyMacro-<kind>` keep the labels UI tests read. When the day's totals change (add, Undo, edit, delete), the calorie total, left/over, bar, and macro grams count to the new values, fast at first and easing onto the final number (about 0.9 s). Totals logged while the card is hidden (add mode) or under a sheet count up once Home is visible again (`SummaryFigures` lives in `MainView`). Switching days and Reduce Motion snap instantly; accessibility labels always report the final values.
- Macro breakdown (October 7, 2026, local): tapping Protein, Carbs, or Fat on Home's summary opens **Today’s macros** (or “Oct. 6th macros”; `MacroBreakdownSheet` in `App/MacroViews.swift`, route `MainSheet.macros`): the day's foods by time with protein/carbs/fat boxes in grams for the whole entry, blank where unknown (a “+” on Home means some foods have no amount). No column is highlighted (blank boxes aren't outlined; owner request); only the box being typed in gets an orange outline. With any blanks, a centered, compact solid-orange **Estimate all missing values ✨** button (`macroEstimateAll`) sits on top, and each row with blanks has a small centered **Estimate missing ✨** under its boxes (`macroEstimate-<row>`); while waiting the sparkles become a spinner. Totals follow what's typed. Unnamed quick-calorie entries read “Quick calories” in gray. The estimate button and column labels stay pinned at the top; only the foods (and the totals row after them) scroll. Blend recent and established habits, smooth food-specific time windows, conditional day patterns, recent meal-session companions, and learned same-day cadence. Preserve replay metrics and avoid random exploration. The pencil/Edit flow opens Add Calories with a separate **Pin on Quick Add** toggle below the serving/time section, and saving applies the final toggle state even if the food name changed.

- Haptics (September 28, 2026, local): every tap gives haptic feedback through `App/Haptics.swift`. Settings → **Haptic feedback** (`hapticFeedback.v1`, on by default, this iPhone only) turns it all off, and UIKit also honors the iPhone's System Haptics switch. Feels: `.tap` for ordinary buttons; `.selection` for pills, segmented/menu pickers, day/week/period arrows, calendar days, option rows, and each new chart column; `.success` when food is logged or something is saved (FoodRow's + plays it only after the add really happens; also Add All, Duplicate, Done eating, toolbar Add/Save); `.warning` for destructive actions (automatic for `role: .destructive`); `.none` where the system already gives feedback. After an add, the calorie count-up rumbles (ticks spaced along the same `UnitCurve` as the animation, then a firm bump when the final number lands). It rumbles only when the total rises; with Reduce Motion it's just the bump. **New features must include haptics:**
  - Buttons get `HapticButtonStyle` from the app root. Never use plain `.buttonStyle(_:)`; use `.hapticButtonStyle(_:)` so an explicit style keeps its haptic, and mark meaning with `.hapticFeel(_:)`.
  - `Form`, `List`, and toolbars reset the button style, so use `HapticForm` / `HapticList` instead of `Form` / `List`, and give toolbar and keyboard-bar buttons `.hapticButtonStyle(.automatic)` (or their own haptic style).
  - Alert and confirmation-dialog buttons call `Haptics.play(_:)` in their action and are marked `.hapticFeel(.none)`, so they play once whether or not the style reaches them.
  - Pickers use `.hapticSelection(on:)`. `NavigationLink` destinations use `.hapticOnPush()`, because a tap gesture on the link blocks navigation.
  - Don't add haptics on top of system feedback (switches, context-menu open, full swipe, wheel pickers, the keyboard). Widgets and Siri can't play haptics.
  - DEBUG builds log each event (subsystem `com.philstarkovich.cavecals`, category `haptics`), so simulator checks can confirm which feel played. How it feels must be checked on a real iPhone.
- Keyboard (September 30, 2026): there is no Done bar over the keyboard anywhere. Every screen or sheet with text fields uses `.tapOutsideClosesKeyboard()` (`App/KeyboardDismissal.swift`, a UIKit tap recognizer on the screen's root view): a tap anywhere that isn't a text field closes the keyboard after the tapped control has handled it, so buttons, switches, and segmented pickers still act on that same tap (closing mid-tap stopped segmented pickers from switching). Mark a field's box, row, or pop-up list (name suggestions, serving and servings presets, the recipe link's Paste) with `.keyboardInputArea()` so taps there keep the keyboard; pass `focus:` when its padding or label should open the field. `selectValueOnTap` rows are marked automatically. Only the part of an area that's showing counts, not the part scrolled under a bar, footer, or the keyboard. Home's search field and the meal food picker's search keep their own behavior (Cancel or scrolling closes them), so several foods can be added with the keyboard up. New screens with text fields must use this instead of a keyboard toolbar.
- Log reminders (September 28, 2026, local): one morning notification a day at most, only while nothing is logged for today: "Nothing logged yet" / "Cave empty today. Log your breakfast?" (the meal is named by time of day; the tap opens search). There's no Home card or button for it. Once someone has logged on 3 different days (same-day logs), iOS's permission prompt appears on its own while Home is idle, and reminders start on if allowed. The timing is learned from each day's first log in the last 21 days, counting only entries logged on the day they belong to: one hour after the median, but never earlier than the 80th percentile, kept within 6 AM–9 PM. Weekdays and weekends learn separately when both have 3+ days and differ by 45+ minutes. It uses 10:00 AM until 5 days are learned. Logging anything today cancels today's reminder (and clears one already showing). Only today plus the next three days are scheduled, and nothing is scheduled after 3 days in a row without logging, so someone who stops gets at most three. It stays quiet while the app is open. Settings → **Reminders**: **Remind me to log** (`logReminders.v1`), **When** Learn from my log / At a set time (`logReminderMode.v1`, `logReminderTime.v1`, default 9:00 AM), a footer showing the learned time, and a link to iOS Settings if notifications are denied. Timing lives in `LogReminderPlan` (`App/LogReminders.swift`, unit-tested). The prompt never appears with `--uitesting` or `--screenshots`. The iOS prompt and delivery need a signed device check.

## Verification and release discipline

- Preserve existing uncommitted user changes. Use focused diffs, build checks, and relevant behavioral tests; cosmetic-only changes do not need new tests.
- Useful simulator test cases in `UITests/ECCUITests.swift`: unified search/list restoration, search-add transition/Undo, and brief background tab preservation. Logging shortcut tests are in `UITests/LoggingActionUITests.swift`.
- A simulator build does not validate physical camera, App Attest, CloudKit production sync, or sandbox subscriptions. State those limits accurately.
- For simulator builds: `xcodebuild -project CaveCals.xcodeproj -scheme CaveCals -sdk iphonesimulator -configuration Debug CODE_SIGNING_ALLOWED=NO build`.
- For simulator UI tests, pass `CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=-` so the app and test runner have fresh ad-hoc signatures. Unsigned incremental test runs can reuse a stale installed runner; do not treat an old source-line failure as validation of the latest helper.
- For device tests, discover current simulator/device IDs instead of hardcoding historical IDs. Keep app/widget version and build numbers consistent in release archives.
- Build releases from `main`. Each uploaded build's commit is tagged (`v1.0.4-build2`). `main` had stayed at 1.0.3 until October 1, 2026, when the 1.0.4 work was merged into it.
