# Cave Cals project guidance

## Scope and architecture

- Native SwiftUI / SwiftData app, iOS 17+, project and scheme `CaveCals`, bundle `com.philstarkovich.cavecals`. ECC2 is an alias of this repository.
- iPhone is the target device family. Verify core functionality on iPad in iPhone compatibility mode too, especially subscriptions.
- Backend instructions are in `backend/AGENTS.md`; read them before backend work. Preserve local-first manual logging and server-verified paid AI access.
- Read `README.md` for architecture and `Documentation/Release/Readiness.md` for dated release evidence. Never confuse local changes with an uploaded TestFlight build.

## Current UI decisions (updated September 25, 2026)

- Two states on one screen. **Home**: date header (person + chart + cog), the `DailySummaryCard`, then the day's log under a small orange left-aligned “Today” label (or the date, e.g. “Sept. 22nd”; shown only once something is logged). While today has nothing logged, Home shows **Quick Start** (orange lightning label, `homeQuickAddHeader`) below the log: up to ten Quick Add picks in a short scrolling list (`homeQuickStartList`) sized to three and a half rows, with the half row fading out to invite scrolling. Names stay on one line with an ellipsis so every row is the same height. Its cards are inset 28 pt from the screen edges and use `FoodRow(compact:)`: 16-pt one-line names, 17-pt calories, a 29-pt + circle, and 44-pt rows. The empty-day message reads “No log yet.” They stay while being used, so several can be added; an added pick leaves after its confirmation (the next suggestion fills in, existing rows never reorder) unless it's usually logged more than once a day and today's count is below that usual number (`FoodHistory.expectsAnotherToday`). Search/add mode, Voice Log, Meal Scan, or Barcode Scan while viewing Today retires the picks for the rest of that day (`homeQuickAddDay.v1`); backfilling another day does not. A small gray × right-aligned on the “Quick Add” label row (lined up with the + buttons, `dismissHomeQuickAdd`) also hides them for the day. Settings → Home → **Show Quick Start on new days** (`showsHomeQuickAdd.v1`, on by default, local only) turns them off entirely. The header date shows “Today” followed on the same line by the full date (“Fri, Sept. 25th”) in small gray text, with extra space between them and tighter spacing to the chevrons; every other day (including yesterday) shows only the full date. No pills on home. **Add mode**: tapping the search field hides the date and totals and shows the pills **Logged** (labelled “Today”/the date; identifier stays `Logged`) with the hand-drawn checkmark, **Quick Add** (selected on entry) with the lightning bolt, and **Meals** with the covered dish; the search field goes full width and the capture icons hide. **Cancel** (the in-field button when empty) returns home. An orange back chevron (`addModeBack`) sits inline just left of the pills and also returns home. Do not use emoji in the pills or add a duplicate Suggestions heading.
- The app opens on Home with the keyboard closed. Brief background/foreground transitions preserve the state, query, and date; after at least 30 minutes in the background reset to today's Home. The Search/Add shortcut opens add mode with the field focused; other logging shortcuts open their requested action. Day rollover remains supported.
- A single search field stays anchored at the bottom beside the voice, barcode, and meal-scan actions. The footer occupies its own fixed-height row below the clipped scrolling list (not a bottom safe-area inset); it moves above the keyboard, with reminders above the controls. No log rows may appear beneath the footer. There is no Quick Calories grid (removed September 25, 2026); typing a number in search adds calories. Food plus calories (`pizza 300`, `pizza, 300 cal`, `300 cal pizza`; parsed by `QuickEntryText`) shows an `Add "pizza" · 300 calories` row that logs in one tap; a bare trailing number must be at least 10 so counts like `eggs 2` stay searches. No separate Search button or floating Close button.
- Typing replaces the list with existing manual/numeric add, common-food, local-history, saved-meal, and online results and hides the pills. **Clear** empties the text and returns to add mode's pills; **Cancel** returns home. A successful search-result add clears the query, returns home, and scrolls to the newest row, keeping the field focused (keyboard up, **Cancel** in the field) so the next food can be typed immediately. Tapping that focused field opens add mode's pills; **Cancel** or scrolling dismisses the keyboard. The pinned `Add "query"` row above the search field (`manualSearchEntry`) uses the same orange (+) as result rows, lined up with them (20-pt trailing), with 8 pt above and below; it opens the editor to enter calories.
- Search has one red in-field text button: **Clear** while there is text (empties the field, stays in add mode) and **Cancel** when empty (returns home). Identifiers `clearSearch` / `cancelAddMode`. Hide the Results heading for numeric calorie input.
- Each changed search query starts scrolled at the top, including when the matching row IDs are unchanged. API responses arriving for that query do not reset scrolling. History matches resolve synchronously and always appear first, followed by saved meals, built-in foods, then API matches; never alphabetize these sources together.
- Editors, camera, voice, settings, and calendar can still use sheets. Canceling an editor returns to the home screen without creating a search sheet.
- The daily weigh-in reminder is not part of the footer: it's a separate outlined card (orange border, semibold orange text, trailing chevron) on the page just above it, with the dismiss × outside the card. Identifiers `weighInReminder` / `dismissWeighIn`.
- Done eating (September 27, 2026, local only): on Today, once something is logged, a matching outlined card **Done eating for today** (check icon, no chevron; `finishDay`) appears from 6 pm, or earlier once the day reaches 90% of its calorie goal, with × (`dismissFinishDay`) to hide it for the day. Tapping it replaces the search/capture footer with “Day done. Cave closed.” and an orange **Reopen** link (`dayDone` / `reopenDay`) and hides Quick Start. Logged rows stay editable. Logging anything more for today (including Siri, widgets, shortcuts, and Duplicate) reopens it; edits, deletes, and later backfills don't. Only today can be marked; past days keep their marks. Marks live in `finishedEatingDays.v1` (per iPhone, not synced). Settings → Home → **Show “Done eating” button** (`showsFinishDay.v1`, on by default) turns the card off. Progress treats a done day, including today, as complete even when it's below the 60% rule.
- Home log rows show only time, food name, and calories, without a macro line. Names/calories use 18-point adaptive Schoolbell text with primary color at 0.92 opacity; narrow time-to-description spacing and compact rows. Home's log rows (content and card, `homeLogOpacity`) sit at 80% opacity so the totals above lead; the “Today” label, Quick Start, and add mode's Today list stay full strength. Header spacing is deliberately tight. Tapping a logged row edits it (the editor opens with the calories selected so typing replaces them). Swiping left shows a gray **Duplicate** beside the red **Delete**; a full swipe deletes. Long-press offers Edit / Duplicate / Delete. Duplicate logs a new copy on that day at the current time. Keep swipe-to-delete red for meal rows too; do not let the orange app accent tint destructive actions. Logged rows end with a gray, non-interactive pencil.
- The home summary is one `DailySummaryCard`: a 52-point adaptive Schoolbell calorie total with a tighter top inset (thickened with `InkBoldText`, since Schoolbell has no bold weight) with `/ 2,100 cals` (or `cals` without a goal) and “N left”/“N over” (red) on one baseline, then a 10-pt calorie bar (orange; red when over goal). When macros are tracked, three columns show, each centered in its column, a hand-drawn orange cave icon (`CaveProtein`/`CaveCarbs`/`CaveFat`, sized by height so narrow art keeps no side padding) + uppercase name (centered on only half the icon's width, so the name sits slightly left) and a bold whole-gram amount with `/ goal g`, above a full-width thinner 6-pt bar that stays orange past the goal (exceeding protein is often intended). No percentages. Accessibility identifiers `calorieSummary` and `dailyMacro-<kind>` keep the labels UI tests read. When the day's totals change (add, Undo, edit, delete), the calorie total, left/over, bar, and macro grams count to the new values, fast at first and easing onto the final number (about 0.9 s). Totals logged while the card is hidden (add mode) or under a sheet count up once Home is visible again (`SummaryFigures` lives in `MainView`). Switching days and Reduce Motion snap instantly; accessibility labels always report the final values.
- Home background (September 27, 2026): use plain `caveBackground`. The handprint, mammoth, and campfire overlay was removed at the owner’s request to reduce visual complexity. Do not restore decorative background artwork. Keep supplied icons, launch art, and mascots unchanged.
- Theme: cream backgrounds (`Color.caveBackground`), lighter cream surfaces (`caveSurface`), and burnt-orange accent (`caveOrange`, also the AccentColor asset), defined in `Shared/CaveIcon.swift` with dark variants. Selected pill is solid orange with white text. Pills size to their labels and share leftover width evenly (`PillRowLayout`), so Quick Add is wider than Today/Meals. Logged and Quick Add rows sit on lighter rounded cards (`caveCardRow()`) instead of separators; the rule under the pills shows only above an empty list.
- On Quick Add, Meals, and Review Scan rows only the orange + adds; tapping the name or calories opens the editor, like the pencil.
- Quick Add rows show food names and calories without macro values. They use a 52-point minimum height with zero vertical list insets. Preserve at least 44-point controls and allow text to grow for accessibility.
- Quick Add ranking is local and deterministic and shows up to ten foods. Blend recent and established habits, smooth food-specific time windows, conditional day patterns, recent meal-session companions, and learned same-day cadence. Strongly suppress an already-logged food only when its history indicates it is normally logged once daily; repeat foods recover according to their typical daily count and gap. Preserve replay metrics and avoid random exploration. User-pinned foods occupy the first Quick Add positions in pin order and count toward the ten-item limit; remaining positions retain algorithmic order.
- Quick Add rows can be hidden for 2 weeks: swipe left for a gray **Hide** (not red) or long-press → **Remove, No Add Often** (renamed from “Hide for 2 weeks” September 29, 2026; same 2-week snooze), with the standard Undo banner. Hiding unpins the food; logging it again ends the snooze early. Settings lists “Hidden from Quick Add” with return dates and **Unhide**. Snoozes are local preferences (`hiddenQuickAddFoods.v1`), not synced.
- Long-pressing a Quick Add row shows **Edit**, **Add**, and **Pin** (or **Un-Pin**). Pinned rows show a pin icon immediately before the food name. The pencil/Edit flow opens Add Calories with a separate **Pin on Quick Add** toggle below the serving/time section, and saving applies the final toggle state even if the food name changed.
- The Meals home list replaces the former Settings → Meals screen. It shows meal name, calorie total, pencil, and orange add circle without repeating the Meals icon on every row. Separate the compact centered **New Meal** button from the first meal with a top border. Long-press offers **Edit**, **Delete**, and **Pin/Un-Pin**; pinned meals stay first and show a pin icon. New Meal opens a chooser of five icon cards (From today’s log, Snap your meal, Say what’s in it, Import a recipe, Build it yourself; identifiers `newMealToday`/`Photo`/`Voice`/`Link`/`Manual`), with the fixed red bottom **Cancel**. Photo, voice, and link results seed the normal New Meal editor for review before saving. The editor can combine ticked day entries (with Select All) and extra foods; the name is optional and defaults to a time-of-day name (Breakfast/Lunch/Dinner/Snack, numbered if taken). The Add food picker stays open for several foods (checkmarks + “N added”) until **Done**. Shortcut: **Save as Meal** under Review Scan’s Add All (the day’s log has no Save as Meal row; use New Meal → From today’s log).
- Haptics (September 28, 2026, local): every tap gives haptic feedback through `App/Haptics.swift`. Settings → **Haptic feedback** (`hapticFeedback.v1`, on by default, this iPhone only) turns it all off, and UIKit also honors the iPhone's System Haptics switch. Feels: `.tap` for ordinary buttons; `.selection` for pills, segmented/menu pickers, day/week/period arrows, calendar days, option rows, and each new chart column; `.success` when food is logged or something is saved (FoodRow's + plays it only after the add really happens; also Add All, Duplicate, Done eating, toolbar Add/Save); `.warning` for destructive actions (automatic for `role: .destructive`); `.none` where the system already gives feedback. After an add, the calorie count-up rumbles (ticks spaced along the same `UnitCurve` as the animation, then a firm bump when the final number lands). It rumbles only when the total rises; with Reduce Motion it's just the bump. **New features must include haptics:**
  - Buttons get `HapticButtonStyle` from the app root. Never use plain `.buttonStyle(_:)`; use `.hapticButtonStyle(_:)` so an explicit style keeps its haptic, and mark meaning with `.hapticFeel(_:)`.
  - `Form`, `List`, and toolbars reset the button style, so use `HapticForm` / `HapticList` instead of `Form` / `List`, and give toolbar and keyboard-bar buttons `.hapticButtonStyle(.automatic)` (or their own haptic style).
  - Alert and confirmation-dialog buttons call `Haptics.play(_:)` in their action and are marked `.hapticFeel(.none)`, so they play once whether or not the style reaches them.
  - Pickers use `.hapticSelection(on:)`. `NavigationLink` destinations use `.hapticOnPush()`, because a tap gesture on the link blocks navigation.
  - Don't add haptics on top of system feedback (switches, context-menu open, full swipe, wheel pickers, the keyboard). Widgets and Siri can't play haptics.
  - DEBUG builds log each event (subsystem `com.philstarkovich.cavecals`, category `haptics`), so simulator checks can confirm which feel played. How it feels must be checked on a real iPhone.
- Log reminders (September 28, 2026, local): one morning notification a day at most, only while nothing is logged for today: "Nothing logged yet" / "Cave empty today. Log your breakfast?" (the meal is named by time of day; the tap opens search). There's no Home card or button for it. Once someone has logged on 3 different days (same-day logs), iOS's permission prompt appears on its own while Home is idle, and reminders start on if allowed. The timing is learned from each day's first log in the last 21 days, counting only entries logged on the day they belong to: one hour after the median, but never earlier than the 80th percentile, kept within 6 AM–9 PM. Weekdays and weekends learn separately when both have 3+ days and differ by 45+ minutes. It uses 10:00 AM until 5 days are learned. Logging anything today cancels today's reminder (and clears one already showing). Only today plus the next three days are scheduled, and nothing is scheduled after 3 days in a row without logging, so someone who stops gets at most three. It stays quiet while the app is open. Settings → **Reminders**: **Remind me to log** (`logReminders.v1`), **When** Learn from my log / At a set time (`logReminderMode.v1`, `logReminderTime.v1`, default 9:00 AM), a footer showing the learned time, and a link to iOS Settings if notifications are denied. Timing lives in `LogReminderPlan` (`App/LogReminders.swift`, unit-tested). The prompt never appears with `--uitesting` or `--screenshots`. The iOS prompt and delivery need a signed device check.
- Rating prompt (September 29, 2026, local): after the fifth food logged on one day (any day, first day of use included) or a tap on **Done eating for today**, Home asks **Cave Cals good?** (**Not really** / **Yes! Me like**) once it's idle: no sheet, add mode, focused search field, or pending iOS notification prompt, and never in the same session as that prompt. **Yes! Me like** calls Apple's `requestReview` (Apple decides whether it shows; it never shows in TestFlight). **Not really** follows with **Help fix cave?** (**Send Feedback** opens https://ascbuddy.com/support/6809208501, **Not now**). Asked at most once every 120 days per iPhone (`reviewPromptLastAsked.v1`); policy and links live in `App/ReviewPrompt.swift`. It never appears with `--uitesting` or `--screenshots` unless a DEBUG UI test adds `--review-prompt`, which also skips the cooldown.
- Add feedback rotates forward through 360 degrees: orange plus front, plain unboxed checkmark on a transparent reverse, then orange plus again. Honor Reduce Motion and prevent duplicate adds during confirmation.
- Adding from add mode's Quick Add, Today, or Meals lists stays in add mode and plays the confirmation animation so several items can be logged quickly. Add mode's Today list repeats the day's entries as Quick Add-style rows (calories, pencil, +): + logs a new copy now, and the pencil edits a new copy (the original entry is never changed). Successful search, photo, voice, and barcode additions return home and reveal the newest row.
- The barcode sheet is titled **Barcode Scan**, uses **Cancel** as its navigation action, and does not offer a manual-calorie link. A barcode logged before (a local `BarcodeFood` match) is added immediately with the standard Undo banner and returns home. A new product's lookup replaces the scanner directly with the populated **Add Calories** editor; never stack that editor over the scanner.
- The header shows the date between tight chevrons on the left, then person, chart, and cog icons on the right. The person icon (`profile`) opens **About You**: the calorie plan row first only when no goal is set (orange covered-dish icon, “Build a calorie plan”, gray right chevron), daily calorie goal, macros, weight, then the Cave Cals+ card at the bottom. With a goal set, the calculator entry sits in the goal section's footer (`caloriePlan`): the saved plan's weight goal in smaller black text with an orange pencil (“Goal: 180 lb, about 0.6 lb/week” or “Goal: stay around 180 lb”), or a right-aligned orange **Help me decide** link when the goal was set by hand. Saved answers are cleared from the calculator's first screen (**Clear my saved answers**, `clearSavedAnswers`, with confirmation), not from About You. About You rows share one height (`defaultMinListRowHeight` 60) and whole rows are tap targets. Row labels and recorded values are black; orange is reserved for tappable accents (icons, pencils, toolbar actions), the Build/Update calorie plan text, the Daily calorie goal value ("Set" when unset), and the empty Today’s weight action ("Log"). The goal/weight pencil and value use a 6-point gap and 8 points of extra trailing inset. Inside list buttons use `Color.primary`/`Color.secondary`, because `.primary`/`.secondary` pick up the orange tint. The cog (`appSettings`) opens **Settings**: Cave Cals+ card at the top, developer settings, Appearance, Home (Quick Add at day start), Apple Health (**Calories & macros** and **Weigh-ins** switches; the Track weight switch itself stays in About You), iCloud, **Tell the tribe** (**Rate Cave Cals** opens the App Store write-review page, **Share Cave Cals** shares the App Store link, **Send feedback** opens https://ascbuddy.com/support/6809208501; identifiers `rateApp`/`shareApp`/`sendFeedback`), About/credits, and legal links.
- Progress (September 27, 2026, local): the hand-drawn, gently downward-trending line-chart icon (`progress`, right endpoint about halfway above its baseline) between person and cog opens one scrolling page with the current calendar week's weight/calorie averages, min/max, independent day counts, changes vs the prior week, and daily breakdown. Move weight graphs and All weigh-ins here from About You. Both charts use calendar Week/Month/Year; week/month show daily values, year shows weekly averages clipped at year boundaries. Week starts Monday by default, configurable locally (`progressWeekStart.v1`) for charts/review/print; the weigh-in editor keeps its existing Sunday–Saturday picker. Calories chart defaults to approximate orange-shade protein/carbs/fat + gray unknown, with calories-only and individual macro (grams) filters. Logged calories always determine stacked height; scale known 4/4/9 portions if they exceed that total, unknown fills any remainder.
- Progress averages exclude missing logs; past calorie days below 60% of the preceding 28 calendar days' completed-day average are incomplete. Classify chronologically and exclude earlier incomplete days from later references. With no prior completed data, include the first logged day. Today is in progress and excluded from completed calorie averages. Weight averages independently use recorded weigh-ins. Incomplete daily bars remain visible/faded and labeled; year averages omit them. Individual macro averages use completed calorie days with recorded gram values and show coverage. No missing values become zero and no log data is rewritten. See `Documentation/Progress.md`.
- Weekly Recap uses separate weight/calorie cards with no icons, mini weekly line/bar charts with compact weekday labels and right-side value scales, bold change amounts at the right, ranges prefixed with “Range:” (e.g. Range: 172.2 to 172.8; no units/min/max), and retained included-day counts. Leave space between metric details and the narrower plots; use a smooth monotone weight curve through recorded points and preserve gaps for missing days. Open on the current calendar week, labeled In progress; the back arrow selects previous weeks. Averages and ranges use available data even without a prior-week comparison. Daily breakdown always starts collapsed; changing weeks collapses it. Do not show an incomplete-day count.
- Settings → Saved food nutrition → **Reset Saved Nutrition** removes personal values saved with **Save as default**, after a destructive confirmation. Restore the affected foods' current built-in calories, portions, and macros for future search/Quick Add/Siri/meal-picker adds. Keep diary snapshots, saved meals, barcode foods, goals, weights, pins, and Health records intact. Local `resetCommonFoodIDs.v1` markers prevent old diary values from resurfacing as defaults; saving a new explicit default replaces that marker. The action is disabled when no custom defaults exist. Simulator tests/previews keep food defaults in memory and never reset live preferences.
- Progress print: one-page **Weekly Recap** PDF with full weekday/month/ordinal-day dates for the selected week. Top weight comparison is emphasized versus prior week; top calories compare against the current daily calorie goal, not the previous week. Retain min/max. A horizontal rule separates large dark **Six-Week Trends**, with weekly graphs/table, smaller signed prior-week changes beside both averages, and a tan latest-week row. No calculation/footer notes. End at the selected week, including the current week; label its report In progress. Future weeks are unavailable. AirPrint/PDF sharing stay user initiated. DEBUG simulator `--progress-preview --progress-open` uses isolated sample diary, weights, Health ledger, and week-start preferences.
- Online search results are named by the product (“Diet Coke”, not “Coca-Cola — Diet Coke”); the brand shows in the gray detail line beside the serving. One-word product names keep the brand (“Starbucks Latte”).
- Footer voice, barcode, and meal-scan glyphs render at 36 pt.
- Meal capture pauses the preview connection immediately while retaining the photo capture session; photo settings prioritize speed. Validate actual shutter/preview behavior on hardware.
- Voice Log, Meal Scan (including Review Scan), and the barcode scanner use a fixed, centered red-text **Cancel** action above the bottom safe area. Keep at least a 44-point tap target and do not put Cancel in the top-left navigation bar on these capture surfaces.
- Paywall first: Meal Scan and Voice Log check scan access as soon as they open (in parallel, so paying users see no delay); when scans are used up they discard any capture and show the paywall before anything is uploaded or analyzed. Import a recipe checks Cave Cals+ on open the same way. Declining the up-front paywall closes the capture screen. The backend also refuses uploads, analysis, and imports before any OpenAI call.
- Siri/Shortcuts **Log Food** (`LogFoodIntent`, “Log food with Cave Cals”) asks “What did you eat?” and logs without opening the app. Shorthand with calories, saved meal names, and foods logged before are handled locally for free; anything else goes to `food/describe` (one scan, like a voice log, paywall enforced by the backend) and is logged without a Review Scan step. The spoken reply names what was logged and today's total/left.
- Opening Voice Log (in-app mic, widget, shortcut) starts recording immediately once the app is active; no extra Talk Now tap. UI tests (`--uitesting`) skip auto-start.
- Widget: when today's total exceeds the goal, the word “over” is red. Each orange tile is an App Intent button (including the small widget); Search/Add opens today’s add mode with search focused and the keyboard up, dismissing an existing sheet first. Tapping the totals/background/gaps opens today’s Home with no keyboard or capture sheet via `cavecals://home`. The shared foreground intent queues through `LoggingActionRouter`, including cold launch/onboarding.
- Voice recording uses an accent-colored (orange) microphone pulsing opacity, not a red/orange color animation. The primary button is orange before recording and turns red while its action is **Stop and Analyze**. Use only the fixed bottom Cancel and omit any additional Cancel inside the card. Processing says “Analyzing your meal…”; interrupted/retryable recordings say “Recording saved” with an explicit next step. Never imply analysis is running when it is not.
- Photo/voice estimate review is titled **Review Scan** and uses the same white-name, calorie, pencil, and orange add-circle rows as Quick Add. Do not show an instructional Foods heading. A single result has no bottom action and dismisses after its row is added. Multiple results show **Add All** below the list; individually added rows keep a persistent checkmark and show the standard “item added” Undo banner. Undo removes that entry and restores its row’s plus button. Add All adds only the remaining rows before dismissing. No top-right Add action. Scan details use a centered accent-colored **view scan details** disclosure below Add All (or below the list for one item), with no background on the disclosure itself; expanding it slides a separate filled details panel into view below.
- AI photo and voice results separate a useful human-scale serving size from the number eaten. Naturally countable food uses one item as the serving size (two bananas becomes `1 banana` × `2`); bulk food uses a familiar household, label, volume, or weight unit. Never use microscopic units such as individual rice grains. When no useful base unit is clear, keep the complete portion as one serving. Preserve compatibility with older cached AI results.
- Toolbar food confirmation actions (Add, Add Meal, and the editor’s Save Changes) use solid orange (accent) prominent buttons with white text and a checkmark. Preserve validation/disabled states.
- All 25 cave glyphs in `Shared/CaveIcons.xcassets` are the user-supplied doodle SVGs (September 24, 2026 set), single-color template assets shared by the app and widget. Replace them with new SVGs of the same names; do not regenerate or restyle them without a request. Only the macro icons' viewBox width was tightened to their artwork.
- Keep the supplied launch artwork centered on its matching cream background and the supplied drumstick scan app icon. Do not regenerate artwork without a request. Since September 30, 2026 the launch screen shows the user-supplied portrait logo (caveman with phone and drumstick above hand-lettered CAVE CALS), asset `LaunchLogo` (renamed from `LaunchArtwork` so cached launch screens can't reuse the old art), flattened onto the launch cream (251, 248, 242) because the transparent original rendered blank in the launch snapshot, at 850×1062 px; original in `Artwork/Launch/launch-logo.webp`. `LaunchScreen.storyboard` keeps its 1122:1402 proportions at 72% of the safe-area width. Simulators can keep showing an old launch screen until they are restarted.
- Apple Health food sharing (`NutritionHealthSync`, off by default, per iPhone): writes Dietary Energy plus protein, carbohydrates, fat and fiber (when known) for each entry dated on or after the day sharing was first turned on, with the food name as `HKMetadataKeyFoodType`. Each nutrient uses sync identifier `cavecals.entry.<entryUUID>.<nutrient>` and the entry's `updatedAt` (ms) as sync version, so edits replace, a second iPhone never duplicates, and deletes (including ones arriving via iCloud) remove the samples. It never reads Health data. Pausing keeps the local ledger (`Application Support/AppleHealth/nutrition-v1.json`, excluded from backup) so resuming fills the gap. Simulator builds lack the HealthKit entitlement; verify on a signed iPhone.
- Onboarding is optional and short: welcome, about you, starting measurements, usual activity, goal/pace, **What do you want to track?**, then an editable calorie target. The tracking step (moved off the welcome screen September 29, 2026) has **Track my weight** and **Track macros** switches, both on by default for new users, with no per-switch explanations; it comes just before the target (manual-only results go back through it) and plan revisions skip it. These choices apply to calculated plans, manual targets, and **Just start tracking**; existing users keep their preferences. Both remain changeable in About You. The welcome screen offers **Me Build Plan** (with the hand-drawn right arrow) and **Just start tracking** (no goal); there is no “Set my own goal” shortcut there (removed September 26, 2026). **Just start tracking** first asks **Skip plan?** (“Cave Cals help you pick daily calorie target to reach your goal. Take less than one minute.”): **No, me build plan** starts the plan; **Yes, skip plan** shows the tracking step without a progress bar, whose **Let’s go** finishes without a goal and whose back returns to the welcome. A manual target stays available on the result step when the calculator can’t estimate (minors, clinician-led, Prefer not to say) and later via About You; no paywall or permission requests during setup. Use the local, bounded calculator in `CaloriePlan.swift` and its manual-only paths. Personal inputs stay in the protected local weight file; only the accepted calorie goal follows diary sync. Existing profiles skip onboarding and can revisit it from You.
- Post-onboarding offer (September 29, 2026): after successfully saving a new user's calculated plan, manual goal, or no-goal choices, show the RevenueCat paywall once with a persistent **Skip for now** (`skipOnboardingPaywall`). Setup is saved before the offer; skipping/closing/purchasing/restoring opens Home, and existing members bypass it. Existing profiles and revised plans do not trigger it; developer previews still return to Developer settings without contacting RevenueCat. Skip remains available while loading or unavailable. The annual App Store product has a 7-day free trial in all 175 enabled territories from September 29; monthly retains its 3-day trial. RevenueCat's published introductory text uses `Try for {{ product.offer_price_with_zero }}` and the offer period followed by the annual renewal price; noneligible users see **Continue**. Prices and eligibility come from StoreKit. RevenueCat SDK 5.90.0 renders localized zero (e.g. **Try for $0.00**). Backend purchase verification remains authoritative. This local onboarding change needs a new app build; the store offer and published paywall configuration are already live.

## Verification and release discipline

- Preserve existing uncommitted user changes. Use focused diffs, build checks, and relevant behavioral tests; cosmetic-only changes do not need new tests.
- Useful simulator test cases in `UITests/ECCUITests.swift`: unified search/list restoration, search-add transition/Undo, and brief background tab preservation. Logging shortcut tests are in `UITests/LoggingActionUITests.swift`.
- A simulator build does not validate physical camera, App Attest, CloudKit production sync, or sandbox subscriptions. State those limits accurately.
- For simulator builds: `xcodebuild -project CaveCals.xcodeproj -scheme CaveCals -sdk iphonesimulator -configuration Debug CODE_SIGNING_ALLOWED=NO build`.
- For simulator UI tests, pass `CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=-` so the app and test runner have fresh ad-hoc signatures. Unsigned incremental test runs can reuse a stale installed runner; do not treat an old source-line failure as validation of the latest helper.
- For device tests, discover current simulator/device IDs instead of hardcoding historical IDs. Keep app/widget version and build numbers consistent in release archives.
- Build **1.0.4 (1)** was uploaded September 27, 2026 and verified VALID / IN_BETA_TESTING with explicit Internal Testers membership and owner access. It includes the Progress/Weekly Recap UI and six-week PDF. Later changes need a new build/upload when requested. Verify Apple processing and internal group membership before claiming availability.
- Do not publish an App Store release, alter storefront availability, or claim the review rejection is resolved merely because a TestFlight upload succeeded.
